# خطة انتقال تدريجي إلى Flutter

التطبيق الحالي عميل Android أصلي (Kotlin/Jetpack Compose) ويتصل بخادم Django عند `https://shopik.alattab.site/api/`. الانتقال إلى Flutter ممكن من دون تغيير الخادم، بشرط اعتبار REST API المصدر الوحيد للحقيقة وعدم إعادة تنفيذ عمليات المحفظة أو الطلبات محلياً.

## النهج المقترح

1. **تثبيت عقد API أولاً:** وثّق وغطِّ اختبارات عقود endpoints للتحويل، التغذية، والطلبات في Django. يجب أن يعيد التحقق من التحويل `recipient_name` و`id`، وأن تقبل التغذية فقط بعد تحقق مزود الدفع.
2. **إنشاء عميل Flutter منفصل:** أنشئ مشروع Flutter داخل `flutter_client/` في مستودع جديد أو كحزمة مستقلة؛ لا تخلط ملفات Flutter مع مشروع Android Gradle الحالي. استخدم `dio` و`freezed/json_serializable` لنماذج API، و`go_router` للتنقل.
3. **ابدأ بالشاشات غير المالية:** المنتجات، البحث، المتاجر، السلة، والملف الشخصي. تبقى المحفظة والتحويل والتغذية في التطبيق الأصلي إلى أن تتطابق اختبارات العقود.
4. **انقل العمليات المالية بعد التحقق:** شاشة Flutter ترسل الطلب فقط ثم تحدّث الواجهة من استجابة الخادم أو من `GET /wallet/` و`GET /orders/`. لا يوجد رصيد أو طلب أو تحويل ناجح محلياً قبل قبول الخادم.
5. **الإطلاق التدريجي:** اختبر Flutter داخلياً، ثم أطلقه لمجموعة صغيرة مع تتبع الأخطاء. عند نجاح القياسات، اجعل Flutter العميل الأساسي واستبقِ Kotlin لفترة دعم قصيرة.

## متطلبات قبل البدء

- وصول قابل للتشغيل إلى مستودع Django والبيئة الحية لاختبار المخطط الفعلي.
- توثيق authentication (`Token` مقابل `Bearer`) وحالات الأخطاء لكل endpoint.
- بيئة staging وحسابات اختبار للمدفوعات والتحويلات؛ لا تختبر العمليات المالية على الإنتاج.
